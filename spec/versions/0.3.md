# PSL Version 0.3

PSL v0.3 preserves the v0.1/v0.2 canonical runtime model and adds a small authoring feature for ordered split-based scheduling.

## Scope

### Added

1. Top-level `sequence` for flat `sessions` programs.
2. `language_version: "0.3"`.

### Not Added

1. No new runtime scheduling engine.
2. No new canonical timing primitive in compiled/materialized output.

## `sequence` Source Shape

```yaml
language_version: "0.3"

sessions:
  - id: day1
    name: Day 1
    exercises: []
  - id: day2
    name: Day 2
    exercises: []

sequence:
  repeat: true
  items:
    - session_id: day1
      rest_after_days: 1
    - session_id: day2
      rest_after_days: 2
```

Rules:

1. `sequence` is allowed only with top-level `sessions`, not `blocks`.
2. Sessions must omit `day` and `schedule` when `sequence` is present.
3. Each `sequence.items[].session_id` must reference an existing session.
4. Each session id must appear exactly once in `sequence.items`.
5. `rest_after_days` is an integer `>= 0`.

## Normalization

`sequence` is authoring sugar only and is consumed during validation.

### `repeat: true`

The validator computes the total cycle length as:

`sum(1 + rest_after_days)` across all sequence items.

Each session is then normalized to:

```yaml
schedule:
  type: interval_days
  every: <cycle_length_days>
  start_offset_days: <cumulative prior item length>
```

This reuses the existing repeating schedule engine unchanged.

### `repeat: false`

Each session is normalized to a one-time `day`:

`day = 1 + cumulative prior item length`

where each prior item length is `1 + rest_after_days`.

## Consequences

1. Existing compile/materialize/export code paths remain unchanged.
2. Repeating sequences still require the same schedule horizon rules as other repeating schedules (`calendar.end_date` unless otherwise bounded).
3. Non-repeating sequences behave like authored fixed-day sessions after normalization.
